Cible du MVP

Soumission d'abstract avec score de pertinence live, détection de doublons proposée (validation humaine obligatoire), clustering post-clôture, dashboard organisateur, auth chercheur/organisateur. Single-tenant.

Hors scope (volontairement reporté)

  • Multi-tenance (organizationId) — décision déjà prise, à reprendre plus tard
  • Optuna / réoptimisation des hyperparamètres UMAP+HDBSCAN — hyperparamètres fixes pour le MVP
  • Scheduler automatique du clustering — déclenchement manuel par l'organisateur
  • Facturation, notifications email, providers d'embedding alternatifs, migration Postgres/pgvector
🧭
Logique de répartition : 3 modules métier, un par personne — chacun code sa verticale complète (domain, dao, service, api) plutôt qu'une seule couche. Le module Abstract (Personne 1) expose EmbeddingService/VectorStoreDAO comme interfaces ; les modules Edition/Auth (Personne 2) et Doublons/Audit (Personne 3) codent contre ces interfaces avec une valeur factice tant que Personne 1 n'a pas livré le réel, puis branchent — l'architecture en interfaces du projet est faite pour ça. Le pipeline de clustering se fait à trois une fois les modules individuels fonctionnels : il consomme les sorties des trois (embeddings, éditions, doublons) et alimente le dashboard, donc personne n'est mieux placé seul pour le porter. Le frontend attend que l'API soit posée — sa répartition se décidera à ce moment-là.

Frontend

0/0

Ne démarre pas avant que les endpoints des phases 1 et 2 soient stables. La répartition (par écran, ou à nouveau par personne) se décide à ce moment — liste indicative pour l'instant.

    Qui fait quoi, et comment ça s'articule

    1. Personne 1 — Module Abstract : le cœur du produit — embedding (SPECTER2 + ChromaDB), pertinence, classement, orchestration de la soumission. Les autres modules dépendent de ses interfaces (EmbeddingService, VectorStoreDAO) : à livrer sans traîner en phase 1.
    2. Personne 2 — Module Edition & Auth : gestion des éditions (thème, fenêtre de soumission), authentification et rôles. Le vecteur du thème d'édition appelle EmbeddingService — coder contre l'interface avec un vecteur factice en attendant Personne 1.
    3. Personne 3 — Module Doublons & Audit : détection de doublons (lexicale, indépendante, démarrable tout de suite ; sémantique via VectorStoreDAO, factice en attendant Personne 1) et journalisation des actions clés des deux autres modules.
    4. Phase 2 à trois : une fois qu'on a de vrais abstracts avec de vrais embeddings, de vraies éditions et de vrais flags de doublons, le clustering et le dashboard qui les agrège se codent ensemble — personne n'a une vue complète seul à ce stade.
    5. Phase 3 : le frontend ne démarre qu'une fois l'API stabilisée sur les trois modules + le clustering. Pas de travail frontend en parallèle du backend sur ce projet.
